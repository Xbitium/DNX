DNX is an experimental internet protocol where the name is the address. Machines register a fully-qualified domain bound to a cryptographic key. No visible IPs, no NAT configuration, no port forwarding — and every reply is signed by the machine that owns the name.

Protocol flow

Resolve. Punch. Verify.

STEP 1 — RESOLVE

The living registry

Every node heartbeats to the registry, which binds each name to a (public key, live endpoint) pair — first-come, first-served. Records update in seconds, not TTL-hours.

STEP 2 — INTRO

NATs open themselves

The registry introduces the two nodes; each fires packets at the other, opening both NATs simultaneously. No port forwarding, no VPN, no router settings.

STEP 3 — VERIFY

Identity, not just reachability

Every reply is ed25519-signed by the key bound to the name. identity_verified=true means you reached the machine that owns the name — something ICMP never proved.

Packet anatomy

Same wire. Different brain.

A DNX packet is not magic — it rides inside an ordinary UDP/IP datagram, forwarded by the same routers as everything else. What changes is where the meaning lives: in TCP/IP, the address is numbers in the outer header and identity is nobody's job. In DNX, the numeric layers fade into plumbing, and the layer that matters carries a name and a signature.

A packet today — TCP/IP

IP header — the address src 203.0.113.7  →  dst 198.51.100.22
TCP header port 51512 → 443, seq, flags
Payload your data

Humans manage the numbers (subnets, NAT rules, port forwards), and identity lives nowhere in the packet — you reached an address; proving who answered is TLS's job, bolted on later, above.

A DNX packet — v0.1

IP header numbers — plumbing, invisible to you
UDP header ports — plumbing, invisible to you
DNX envelope — the address and the identity name: mymac.internal.dnxroute.com
pubkey: ed25519 · nonce + timestamp · signature
Payload your data — signed today, encrypted in v0.2

The address is a name, bound to a key. Identity travels inside the packet itself: every reply is verifiable against the key that owns the name. The numbers still exist — but nobody has to see, type, or manage them.

Status

Built in the open, one layer at a time.

v0.1 LIVE

Living registry at registry.dnxroute.com · signed name→key binding · NAT hole punching · identity-verified ping. Proven across the public internet and a residential NAT.

v0.2 NEXT

Encrypted channels (X25519 + ChaCha20-Poly1305) and a reliable stream layer — so real applications ride DNX, ending with ssh into a NAT'd machine entirely over DNX.

v0.3 PLANNED

Relay fallback for symmetric NATs · dnx tunnel port gateway · federated registries with a signed name table.
