DNX Protocol Specification

DNX is an experimental identity-native overlay protocol. It explores whether names can become the network interface humans and applications interact with, while existing Internet transport carries the packets underneath.

1. Overview

Traditional networking separates naming, routing, and identity. DNX combines those concerns around a cryptographically bound namespace. A machine registers a human-readable name, binds that name to a keypair, and uses the resulting identity to rendezvous with other nodes.

DNX v0.1 is an overlay. It runs over existing IP networks and does not require new routers or a new physical network.

2. Architecture

Components

  • Registry — maintains live name bindings and coordinates rendezvous.
  • Node agent — holds the identity key and handles heartbeats and peer traffic.
  • CLI — exposes local controls for registration, ping, and diagnostics.

Flow

node → registry: REGISTER
node → registry: RESOLVE
registry → peer: INTRO / PUNCH
peer ↔ peer: PING / PONG

3. Identity model

Every node generates a keypair. The public key is associated with a name in the registry. The private key never leaves the node. A verified response proves that the machine reached the owner of the name, not just any machine at an address.

4. Security

DNX authenticates nodes with signatures and timestamps. v0.1 is explicit about its limits: payload confidentiality is not yet provided, registry responses need hardening, and symmetric NAT remains a future improvement area.

5. Roadmap

  • v0.2 — signed registry responses and encrypted channels
  • v0.3 — relays for hard NAT scenarios and federation
  • v1.0 — compact binary framing and broader tooling
